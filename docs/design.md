# Vorton 编译器设计

本文件记录编译器与 runtime 的架构和跨层不变量。语言的可观察语法和语义只以 [`lang-spec/`](lang-spec/README.md) 为准；设计公理只以 [`philosophy.md`](philosophy.md) 为准。

## 设计约束

1. **事实只产生一次。** 名称、类型、callee、资源行为各自由信息首次完备的阶段决定，之后以 typed 结构单向传递。
2. **下游不猜测。** 下游不按字符串、叶名称、声明顺序或 span 重建上游事实。
3. **上游不回跑。** 一个阶段完成后，后续阶段不重新执行名称解析或类型推断。
4. **确定。** 相同输入产生相同诊断与相同生成文本。
5. **不支持就明说。** 某个阶段还不支持的构造，报告 `Unsupported` 并指向源码，不当作已检查而放行。
6. **优化不可观测。** 优化不改变求值顺序、effect、panic、资源释放时点或输出。

## 求值顺序

同一表达式内的子表达式按源码从左到右求值：被调函数或 receiver 先于参数，参数、二元运算数、List/tuple/构造字段与字符串插值依次求值。`&&` 与 `||` 短路。赋值的顺序见[类型系统](lang-spec/type-system.md#表达式与语句)：先求目标里的下标与键，再求右侧，写入时才检查目标元素存在。这个顺序由 IR 确定，代码生成照 IR 的步骤逐条输出，不依赖 C 未规定的求值顺序。

## 编译管线

```text
source → token → AST → 名称解析 → 声明检查 → 类型检查 → IR → 移交与借出检查
                                                        → 实例化 → 能力检查 → 尾调用 → C11 → native
```

| 阶段 | 模块 | 职责 |
|---|---|---|
| 词法 | `lexer.rs` | 产生 token 与 span，并为每个 token 记录前面是否有换行 |
| 语法 | `parser.rs`、`depth.rs` | 按换行规则切分语句，产生 AST；不做名称或类型判断；拒绝嵌套超过规范上限的源码 |
| 名称解析 | `resolver.rs` | 解析纯内存的多库项目，给每个声明、绑定与引用一个包含库归属的精确 identity |
| 声明检查 | `prepare.rs` | 检查 supertrait 目标与 trait、effect alias 的声明图无环 |
| 类型检查 | `checker.rs`、`types.rs`、`exhaustive.rs` | 局部双向推断：签名给出参数与返回类型，函数体内推断；每个类型在类型表中只登记一次，按编号比较；模式的穷尽性按 Maranget 算法检查；产出带类型的程序 |
| IR | `mir.rs`、`lower.rs` | 把每个函数降为控制流图：基本块中的每一步只读写写明的位置，临时值与借出都显式，分支与循环都是边 |
| 移交与借出检查 | `borrowck.rs` | 在 IR 上沿边做数据流分析：哪些位置可能已空，哪些借出仍存活、与哪些访问冲突 |
| 实例化 | `mono.rs` | 在 IR 上，泛型函数按调用到达的每组类型实参复制一份，把类型参数换成实参，把类型参数上的 trait 方法调用换成 impl 的函数 |
| 能力检查 | `capabilities.rs` | 在实例的 IR 上检查手写的 `drop` 不会用到 console |
| 尾调用 | `tail.rs` | 按规范的定义找出实例中对自身的尾调用，改写为显式的尾调用终结符 |
| 代码生成 | `codegen.rs`、`codegen/body.rs` | 按每个实例的 IR 生成 C11：一块一个标签，边是 `goto`；为 tuple、struct、enum 与容器生成 C 结构体和辅助函数，并插入计数操作 |
| 构建 | `native.rs` | 调用系统 C 编译器生成可执行文件 |

每个诊断保留 `OriginRef`：库、库内 source 与 UTF-8 字节范围，让诊断回到唯一输入位置。

各阶段都沿语法树递归，递归深度随源码的嵌套增长。公开入口在一个预留 1 GiB 栈的线程上运行全部阶段，结果因此不取决于调用方的栈；规范把嵌套深度限制在 10000 层，这个栈在 debug 与 release 构建下都容得下。解析器在递归中计数，超过上限立即报错，解析完成后再按语法树的实际深度检查一遍（长运算链在这时才知道深度），这次检查到上限即停，自身的递归也有界。

名称解析不读取文件系统。它消费宿主给出的 entry 库、唯一 core 库和显式依赖图；每个可达的非 core 库必须直接依赖 core。命令行工具把单个源文件作为 entry 库，把随编译器分发的 `core/root.vorton` 作为 core 库。

### 当前支持范围

类型检查与代码生成按 Milestone 扩展。目前支持 `Int`、`Float`、`Bool`、`Str`、`Unit`、tuple、struct 与 enum（泛型的按具体类型实参实例化，类型参数暂不能带约束；不能按值包含自身）、`Str` 的[方法](lang-spec/type-system.md#字符串)、`List`、`Map` 与 `Set` 及其[规范列出的方法](lang-spec/type-system.md#容器)、任意类型的 `clone`、下标读写、`for` 遍历 range、列表、Map 与 Set（拿走，或用 `&`／`&mut` 借出）、`match`、`if let` 与解构（含穷尽性检查，可按值或借出）、结构化 `==` 与 `<` `>` `<=` `>=`、`Range<Int>` 值、函数与泛型函数、非泛型类型的固有方法与关联函数、trait 声明、非泛型 struct 与 enum 的 `impl Trait for Type`（core trait 中可以实现 `Display`、`PartialEq`、`Eq`、`PartialOrd`、`Ord`、`Clone`、`Drop`）、经 bound 或具体类型调用 trait 方法（含 supertrait 的方法；比较 trait 的方法只能调用手写的，其余用运算符）、`print`、插值与内建类型的 `to_str()` 经 `Display` 显示、比较运算符经比较 trait 分派、字段、固有方法与 trait 的模块可见性、`let`/`let mut`、`mut` 按值参数、借出的参数、绑定与返回、对变量及其字段的赋值、`if`、`while`、`loop`、`break`、`continue`、`return`、字符串插值，以及 `print`、`assert`、`panic`、`replace`、`swap`。其他构造都报告 `Unsupported`。

`Str` 是不可变的值，用引用计数实现 O(1) 拷贝。`Map` 由运行时里一个通用的按插入顺序的哈希表实现：条目按插入顺序存放，删除留下空位，空位多于条目时整体压实；开放寻址的索引按键找到条目。每个具体的 `Map<K, V>` 只生成键的哈希、判等与释放、复制；`Set<T>` 是值为 `Unit` 的 Map。`List`、`Map` 与含有它们的聚合值是实体：

- **移交还是拷贝由类型决定，能否移走在 IR 上检查。** 类型检查只确定类型和写出的借出。位置在需要值的地方被读取时，降级按类型生成：实体移交，值拷贝，被丢弃的值也一样，所以表达式语句里的实体被移交后立即释放。借出检查核对 IR 里每一次移交的来源：不能经借出、从容器元素或从实现 `Drop` 的值中移走。前向分析找出每处可能已空的位置，之后再使用就是错误。移走变量经字段到达的部分时，整个变量记为已移走，所以一个构造取走的几个部分（一个模式按值绑定的实体部分、一个 `..base` 取走的其余字段）在一条 `Unpack` 里一起取走；没有取走的部分留在原变量里，随它释放。降级产生的临时值按部分记录。`match` 的 guard 在主体原处读取按值绑定的实体部分，guard 成立后才取走，所以被拒绝的分支什么也没有取走。
- **生成代码不需要释放标记。** 移交时把源清零，作用域结束时一律释放并清零，释放清零的值什么也不做。所以不是引用的局部变量在任何时刻要么为空，要么持有自己的值；循环里的局部变量每轮开始都是空的。离开作用域的每条边都释放它的局部变量，包括 guard 拒绝分支的那条；debug 构建在降级之后沿边检查，到达 `return` 时装过值的局部变量都已释放。
- **参数约定。** 按值的参数都归被调函数所有，与其他局部变量一样在返回时释放；调用方传入计数值时先计数一次。借出的参数、绑定、循环变量与返回值在 C 里是指针，使用处自动解引用；借出的不是位置时，先存入临时变量，语句结束后释放。方法就是第一个参数为 `self` 的函数，调用处按 `self` 的写法借出或拿走 receiver。
- **操作数当场取值。** 实参、运算数与构造的字段从左到右求值；从位置读出的值在下一个操作数求值之前就存入临时变量，后面的操作数改变该位置也不影响它。`..base` 写在构造的最前面，它补齐的字段在给定的字段求值之前就取出。
- **借出在 IR 上检查。** 每个 `&` 或 `&mut` 都是 IR 中存入引用局部变量的一笔借出。引用局部变量携带它来源的借出：自己的、它再借出的引用的，以及返回借出的调用的借出实参的。只要携带某笔借出的引用之后还可能被使用，这笔借出就存活，这与 Rust 的 NLL 相同；与存活借出的位置重叠、种类冲突的访问是错误。读取值（包括容器的长度、键与值元素，以及 enum 的变体）从不冲突。写入 `m[k]` 可能插入新键，所以记为对整个 Map 的写入。借出实参与 receiver 的 `&mut` 在调用之前只预留：后面的实参仍可读取其中的值（读取是当场拷贝，不构成冲突），调用时才生效，这时与这次调用其他实参的借出冲突就是错误，所以一个位置以 `&mut` 传入后不能再以借出方式传入这次调用。这比 Rust 宽：Rust 只对自动借出的 receiver 这样做，显式的 `&mut` 实参之后再读该位置会被拒绝。调用返回的借出继续携带生效的 `&mut`。经别名的访问（例如经 `let r = &xs` 的 `r`）使用 `r`，从而让 `r` 的借出保持存活，直接访问 `xs` 时与之冲突，所以别名、`match`、比较运算与 receiver 都按同一规则处理。
- **重叠只判定一次，证明不了的在运行时检查。** 一个访问与仍有效的借出是否重叠，由借出检查里唯一的 `overlap` 判定：路径上有不同字段或不同常量下标就不重叠；下标已知相同（同一个常量，或同一个值位置的副本、之后没有改变过）时一定重叠，借出方式冲突就是编译错误；其余情况只有下标的值能说明，借出检查在 IR 里该访问之前插入一条 `Distinct`，运行时下标全部相等就 panic。这就是规范的“编译期能证明的在编译期检查，证明不了的在运行时检查”：`let` 绑定、调用实参、写入与路径长度不同的位置都走这一个判定。“下标已知相同”由借出检查的前向分析给出：索引临时值记下它是哪个值位置的副本，凡是写入、移走、释放那个局部变量，或者经携带它的 `&mut` 借出的引用写入、把这样的引用传给调用的语句，都让副本失效，所以经别名的修改也看得到。降级不做任何证明：每次求下标都存入新的临时值，临时值属于所在代码块，借出期间一直可读。`Distinct` 是 IR 里显式的运行时代价，以后按公理 5 导出。
- **返回借出。** 返回的引用携带的每笔借出都必须是经借出参数到达的位置。返回借出的调用结果是位置，通过一个指向结果的局部指针访问。
- **检查的工作量。** 一个局部变量持有什么、一个引用携带哪些借出，只在之后还可能用到它的地方才有意义。移交分析与借出携带分析在块的边界只保留这些活跃的局部变量，状态按局部变量索引，每一步只看它涉及的局部变量；所以检查的工作量随各处活跃的局部变量增长，而不随函数的局部变量总数增长。类型检查不再重复作用域：名称解析已给每个绑定唯一的身份。
- **IR 校验。** 降级之后与实例化之后各运行一次 `verify.rs`：只有 `Bind` 持有借出，`Copy` 只用于值，`Inspect` 只出现在 `Glue` 里，普通运算符只作用于没有部分的值，位置的每一步都与类型相符，`Unpack`、`Keep`、`Distinct` 的形状正确。违反就是编译器的错误，任何构建下都同样报告，所以 release 构建不会为 debug 构建会拒绝的 IR 生成代码。- **自身尾调用。** 是否是尾调用由实例化之后的一个 IR 阶段按规范的[定义](lang-spec/type-system.md#尾调用)判定，结果写成显式的尾调用终结符，代码生成照做：调用之后到 `return` 只剩释放；借出实参都指向借出参数之后的位置（沿引用局部变量的来源追溯）；调用时可能还持有值的局部变量里没有带手写 `Drop` 的值（用“可能持有值”的前向分析）。终结符生成为跳转：实参先作为有所有权的值存好，释放局部变量，再写入参数，跳回函数开头。不返回的函数（返回 `Never`）调用自身也一样，跳转前释放全部局部变量。
- **Map 的遍历。** 遍历按条目位置从头到尾，跳过删除留下的空位，不为遍历压实，所以遍历前取得的指向条目的借出仍然有效。遍历期间容器被借出或被循环拿走，结构不会改变。

泛型函数只检查一次：类型参数在类型表中是独立的类型，没有 `Copy` bound 的按实体对待。调用处从左到右用实参的类型确定类型实参，仍未确定的再用调用的期望类型。每个函数只降为 IR 一次，移交与借出也只在泛型的 IR 上检查一次。之后，实例化阶段从非泛型函数出发，为调用到达的每组类型实参复制一份 IR 并代入实参；代入后成为值类型的移交照样取走值，借出检查已保证被移走的位置不再使用。结构体与枚举的字段只按自身的类型参数解析一次，得到模板，任何实例都由类型表在模板上代入，所以实例化不需要回到源码。规范对多态递归的限制保证实例只有有限个。代码生成只看到实例。

Trait 方法的调用在检查时就确定到 impl：具体类型直接调用其 impl 的函数；类型参数上的调用记为“该 trait 的第几个方法”，实例化时按类型实参换成对应 impl 的函数。检查器在每个调用处核对类型实参满足 bound，所以实例化时 impl 一定存在；内建类型的 `Display` 没有 impl，`to_str` 实例化为字符串插值。

类型的性质（是否实体、是否需要释放、能否比较、能否作 Map 键、释放时会不会运行 `drop`）都从这个类型出发，把能到达的类型各看一次来判定，所以共享或递归的类型图也只花线性时间。递归类型能否比较取规范要求的最大不动点，它等价于“能到达的类型各自都不排除比较”。能否作 Map 键取决于手写的 impl，而有些类型在 impl 收集之前就要解析，所以解析时只登记键的使用与位置，impl 收集完后统一判定。

比较运算符不经过方法调用：`==` 与 `<` 等对每个具体类型生成一个比较函数，有手写 impl 的类型由它调用手写的 `eq` 或 `partial_cmp`，其余逐字段比较。类型表记录每个类型手写的比较 impl，结构化比较也因此在字段处调用手写的比较。手写的 `Clone` 与 `Drop` 同样记在类型表里：复制与释放该类型的函数调用它们，所以容器与外层结构复制、释放元素和字段时也会调用。

**IR 显示每一处对用户代码的调用。** 除了释放时的 `drop`，能运行用户代码的步骤只有两种：调用函数的 `Call`，以及 `Glue`——有部分的值之间的比较、`clone` 与 `List.contains`。“一种运算作用在某个类型上，是调用手写实现，还是对哪些部分做什么运算”只在 `Types::glue` 描述一次：代码生成的辅助函数据它决定调用谁，能力检查据它找出会被调用的手写实现。分析 IR 的代码对每种步骤穷尽匹配，新增一种步骤时必须说明它会调用什么。`drop` 不计入，因为规范规定它没有 effect，也不能使用能力。拷贝值只增加计数，不运行用户代码（debug 构建会检查这一点）。

实现 `Drop` 的类型在 C 结构里多一个存活标记：构造时置位，移交时随源一起清零，释放函数只在标记置位时先调用 `drop` 再释放字段。字段全是值的这种类型因此也能区分“已移走”和“值恰好为零”。规范不许 `drop` 在 0.1 使用 console：实例化之后，检查器沿实例的 IR 找出每个函数调用的函数与 `Glue` 运行的手写实现，`drop` 能到达 `print` 就是错误。

公开接口不能出现私有的类型或 trait：`pub` 函数的签名与 bound、`pub` 类型的 `pub` 方法签名与关联类型、`pub` trait 的方法签名、关联类型与 supertrait、`pub` struct 的 `pub` 字段，以及 `pub` enum 的 payload。私有类型的方法不论自身是否 `pub` 都到不了模块之外，所以不检查。检查对声明种类与成员种类穷尽匹配、把签名按字段拆开，支持新的声明形式时必须决定它的哪些类型属于接口。

## Runtime

Runtime 是 [`runtime/vorton_runtime.c`](../runtime/vorton_runtime.c)，编译器把它放在每个生成的翻译单元开头，所以每个程序都是单个 C 文件。

- `Str` 是不可变的 UTF-8 字节串，带引用计数。字符串字面量是静态对象，引用计数为负，从不计数或释放。
- 生成代码的约定：局部变量、临时变量与按值参数各自持有一个计数，借出的参数不持有；作用域结束、`break`、`continue` 或 `return` 时释放本作用域持有的字符串。
- `Int` 运算用 `__builtin_*_overflow` 检查溢出，除零与 `INT64_MIN / -1` 显式检查，因此需要 clang 或 gcc。
- `Float` 的文本形式按规范实现：用 `%.*e` 从 1 位到 17 位寻找能读回原值的最短表示，再按 ECMAScript 规则排版。
- panic 向标准错误输出 `panic: <信息>`，以退出码 101 结束。规范不规定这段文字和退出码。
- 定义 `VT_CHECK_LEAKS` 编译时，runtime 统计存活的堆字符串；程序正常结束时若不为零，就报告并以退出码 102 结束。测试总是这样编译。

C 编译参数固定为 `-std=c11 -O2 -ffp-contract=off -fno-fast-math`，保证 binary64 运算不被合并成 FMA 或改写。

## 命令行与测试

- `vorton run <file>`：编译并运行；`vorton build <file> [-o <output>]`：生成可执行文件，中间的 C 文件写在临时目录里，不碰输出路径旁的文件；`vorton c <file>`：输出生成的 C。
- C 编译器取 `VORTON_CC`，否则依次尝试 `clang`、`gcc`、`cc`。
- `cargo test` 除了编译器自身的测试，还运行仓库根目录 [`tests/run/`](../tests/run) 下的每个程序：`<name>.expected` 是期望的标准输出，`<name>.panic` 是期望的 panic 信息。这些程序大多移植自旧版本的测试语料。
