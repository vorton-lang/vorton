# Vorton 设计哲学

Vorton 是一门不默认信任程序员的 native 编程语言。编译器负责推断并检查类型、effect、资源与穷尽性；程序员不必先提交大量证明式标注，但任何无法证明安全或一致的边界都必须显式暴露。接近 Python 只指低标注体验，不表示换行或缩进参与语法。

语言的可观察规则以 [`lang-spec/`](lang-spec/README.md) 为准，编译器分层与不变量以 [`design.md`](design.md) 为准。本文件只保存用于仲裁设计取舍的公理。

## 出发点

人类和自动化程序员都会遗漏条件、误解全局状态并产生不一致实现。人工审查不能随代码量无限扩展，测试也只覆盖已经想到的路径；编译期语义可以从构造上排除整类错误。因此 Vorton 把可机械判断的责任交给编译器，并把剩余人工责任压缩为显式、可枚举的边界。

这一立场对 LLM 尤其有价值，但不依赖 LLM 才成立。衡量一项语言能力时，首先问它能否把真实的人类判断移交给确定、可终止的编译期检查，而不是它是否增加了表面表达力。

## 公理体系

| 层 | 性质 | 公理 |
|---|---|---|
| 0 | 目标 | 4. 不信任程序员，编译器是最终权威 |
| 1 | 硬约束 | 5. 编译器必须终止；6. 资源语义确定；7. 核心场景不可堵死 |
| 2 | 设计策略 | 1. 类型即模型；2. Effect 即可见性；3. 推断为王；8. 一种事一种写法；9. 借用熟悉语法 |

层级用于仲裁而非排序：策略必须服从硬约束；策略之间以能否减少错误和迭代成本为准；修改硬约束或目标属于用户保留决定。

### 1. 类型即模型

类型用于表达真实问题，不用于展示类型技巧。一个类型特性必须让常见用例在低标注模式下可用，并在推断失败时给出可操作的诊断。表达力不能抵消不可判定性、隐式行为或无法解释的失败。

### 2. Effect 即可见性

函数可能发生的宿主访问、失败、共享 mutation、unsafe obligation 与用户自定义 effect 都进入可推断的 effect contract。不同 effect class 可以有不同执行与消除规则，但不能因后端、外部函数或 builtin 边界而从签名中消失。

System effect 只描述静态宿主能力，不能被用户 handler 截获；用户声明的 handled effect 才由 `handle...with` 提供动态解释。Failure、mutation 与 unsafe 各使用自己的消除规则，不能被宽泛 handler 偷换。

### 3. 推断为王，标注为仆

类型、effect、参数 mode 与 capture 尽量由编译器从程序推断。显式标注是契约或对推断结果的 assertion，不得覆盖真实推断；不一致必须产生诊断。格式化工具可以物化推断结果，但不能改变程序语义。

### 4. 不信任程序员，编译器是最终权威

编译器必须追踪类型、effect、资源转移、穷尽性和模块身份，并拒绝无法满足语言不变量的程序。新增机制只有在承担一项明确判断时才有价值；仅把错误推迟到 runtime、后端或人工 review 不算完成。

由此得到三条直接规则：

- 失真必须响：源码、声明与推断事实不一致时不能静默选择一方。
- 优化不可观测：重排、复用、unboxing 与 RC 消除不得改变求值、effect、failure 或 Drop 行为。
- 人工责任必须可枚举：无法由安全语言证明的前提只能存在于显式 `unsafe` discharge 点。

### 5. 编译器必须终止

名称解析、类型与 effect 推断、trait selection、穷尽性和资源规划必须在有限状态上运行。可能无界的搜索必须限制在可判定片段，或以明确上限终止并要求更具体的源码信息；卡死和依赖偶然超时都不是合法编译结果。

### 6. 资源语义确定

资源释放是语言语义，不是垃圾回收策略。`Drop` 在词法 scope 退出时发生；只有证明提前释放不可观测时，优化器才可依照 as-if 规则提前执行。用户 `Drop` 或可被 `Weak<T>` 观察的目标固定在 scope-end。

内存由 ownership 与引用计数管理，不引入 tracing GC 或 cycle collector。无环值必须精确回收；环由显式 `Weak<T>` 打破。确定性不等于常数延迟，级联析构仍可能形成可预测的单点工作量。

### 7. 核心场景不可堵死

CLI、服务端与系统编程必须保有 native、无强制托管 runtime 和清晰 C ABI 的实现路径。语言级事实先在后端无关 IR 中闭合；后端只能机械投影，不能把语义锁入某个进程内专有 API。

### 8. 一种事只有一种写法

同一语义不保留多套等价表面。纯粹少写字符不足以证明语法糖的价值；语法糖必须提供独立的建模、认知、验证或组合能力。

因此 Option 类型只写 `Option<T>`，postfix `expr?` 只表示传播；函数与 closure 都使用 `fn`；方法调用使用 `.method()`，模块路径使用 `::`，两者不互相回退；Vorton 不提供与这些形式等价的第二套拼写。

### 9. 借用熟悉语法

没有独特语义时优先借用已有语言中稳定、常见的写法。`fn`、`let`、`struct`、`enum`、`match`、`trait` 与 `impl` 延续熟悉含义；字符串插值使用 `${...}`；注释使用 `//`。`handle...with` 与 `catch` 承担 Vorton 独有的 effect 语义。

## 错误处理

`Option<T>` 是数据，`fail<E>` 是计算 effect。Option 表达“有或没有”，且只由 `Some(T)` 与 `None` 构成；failure 默认沿调用链传播。`catch` 对 failure payload 做穷尽匹配并消除被处理的 failure；`handle...with` 为用户 handled effect 提供动态解释。把 failure 保存为普通数据属于库层选择，不是第二套语言错误机制。

不可恢复的 panic 与可处理的 failure 不互换。编译器必须保持二者的控制流、资源清理和 effect contract 区别。

## 类型与组合

数据抽象由 `struct`、`enum` 与 `trait` 构成，不引入 class 或继承。Trait 表达行为而非身份；组合通过普通字段、显式 impl 与泛型约束完成。方法解析、关联类型、supertrait 和 dictionary evidence 必须落到唯一声明身份，不能按名字或后端约定猜测。

默认不可变，`let mut` 显式允许 rebind。参数的 borrow、mutation 与 ownership transfer 由推断决定；可选 mode/capture 语法只用于声明或核对该结果。

## 性能地位

性能是工程目标，不是凌驾于语言公理之上的保证。类型、effect、linearity 与 purity 是优化燃料；若某项优化无法证明观测等价，就必须放弃优化而不是放宽语义。性能证据必须来自明确负载和可复现测量，不能由架构宣称替代。

## 偏好约束

| 维度 | 选择 |
|---|---|
| 范式 | 过程式与函数式组合，不引入 OOP 语义 |
| 命名 | `snake_case`，常量使用 `ALL_CAPS` |
| 可变性 | 默认不可变，`let mut` 显式允许 rebind |
| 数据 | `struct`、`enum`、`trait` |
| 内存 | Ownership、Perceus-style RC、确定性 Drop、无 GC |
| 注释 | `//` 行注释，无块注释 |
| 目标 | 后端无关语义，经 C11 路径生成 native 程序 |
